# TAGRO ECHO OS — Pre-Action Reference Directive

Status: Owner-required operating directive
Effective: 2026-08-22
Applies to: every substantial AI/human action affecting architecture, data, runtime, warehouse, integration, UI/UX, deployment or business workflow.

## Directive

Before acting, the builder must establish **what ECHO already knows** and **what the current system already proved**.

The builder must not begin from chat memory, filenames, visual familiarity, a convenient old implementation or a preferred tool.

## Mandatory reference sequence

1. Read the active Constitution and constitutional amendments.
2. Read Foundation Manifest and Current State.
3. Read Decision Ledger.
4. Read Historical Engineering Memory and machine-readable History Index.
5. Read the active Work Order.
6. Read every affected contract/schema/file completely before changing it.
7. Read latest relevant test/session evidence.
8. Inspect the actual current data/runtime/deployment environment when the action depends on it.
9. Identify the predecessor/superseded approach for the same problem.
10. State the intended change in terms of reality, evidence, user/job, data path and expected consequence before mutation.

## No regression by missing context

If the proposed action resembles a superseded or failed pattern, stop implementation until the builder can state:

- what earlier pattern it resembles;
- why ECHO moved away from it;
- what new evidence now changes the comparison;
- whether the old idea is being reused only as a proven skill, or whether the architecture itself is being reconsidered;
- the Planar/Prismatic implications across all affected receivers.

A missing old chat is not evidence that an old approach should be rebuilt.

## Data-first diligence

For any page/report/intelligence feature, the builder must first answer:

- What is the authoritative/shared working data source?
- What source feeds it and how fresh is it?
- What write path persists new events?
- What read path retrieves current and historical information?
- What provenance distinguishes source history, imported working material and ECHO-generated events?
- Which projections/planes may be derived without collapsing separate truths?
- What downstream systems (BUSY, logistics, payments, reports, Observer/BIS) consume or return evidence?

No page may create a new parallel truth store merely because a UI needs data quickly.

## Action declaration

Before a substantial mutation, the builder records or states:

`REFERENCES READ -> CURRENT REALITY -> PROBLEM -> PROPOSED CHANGE -> AFFECTED PLANES/RECEIVERS -> TEST/READBACK -> ROLLBACK`

The declaration may be concise, but it must be real.

## Completion discipline

After action, update durable memory when a material lesson changed the preferred method, and report only what was actually changed/proven/deployed.

## Principle

**Reference before action. Read before rewrite. Prove before claim. Preserve learning before moving on.**
